# Configuração da Orquestração Local

Este guia detalha o ambiente de dupla orquestração utilizado no monorepo. O desenvolvimento local utiliza duas pipelines de containers especializadas:

- **Podman Compose via Podman Desktop**: Usado para codificação local rápida, testes de banco de dados e fluxos de trabalho gerais do desenvolvedor usando containers daemonless.
- **Kubernetes via Minikube & Skaffold**: Usado para validar configurações, roteamento, descoberta de serviços e políticas de ambiente semelhantes à produção com recarregamento dinâmico automático (hot-reloading).

---

## Pré-requisitos de Ferramental

Para rodar e gerenciar o ambiente de orquestração local, instale as ferramentas apropriadas em sua máquina.

### 1. Podman Container Engine & Podman Desktop

Para codificação local rápida de microsserviços e testes de banco de dados:

- **Podman Desktop**: Interface gráfica e gerenciador de máquinas Podman daemonless rodando sob WSL2 no Windows.
- **Podman CLI & Podman Compose**: Ferramentas CLI para gerenciamento de containers e pods.
- **Comando de instalação (PowerShell)**:
  ```powershell
  winget install RedHat.Podman-Desktop RedHat.Podman
  ```

#### Extensões Necessárias do Podman Desktop

Dentro do Podman Desktop (**Settings -> Extensions**), garanta que as seguintes extensões estão instaladas e ativas:

1. **Podman Extension**: Extensão principal para gerenciar máquinas Podman, imagens, containers e volumes.
2. **Compose Extension**: Necessária para analisar e executar fluxos de trabalho do `podman compose` para desenvolvimento multi-container.
3. **Kubectl CLI Extension**: Integra controles de cluster `kubectl` e alternância de contexto do Kubernetes diretamente dentro do Podman Desktop.

:::info[Política de Sem Aliases de Shell]
Os scripts do nosso projeto invocam explicitamente o `podman compose` e o `podman exec` diretamente no [package.json](file:///D:/projects/tupynambalucas/package.json). Não crie aliases de shell (como `alias docker=podman`). O uso de comandos `podman` explícitos garante execução reproduzível em todas as estações de trabalho de desenvolvedores e pipelines de CI.
:::

---

### 2. Ambiente Kubernetes (Minikube via Podman)

Para testes locais de Kubernetes, validação de roteamento e pipelines de implantação, usamos o `minikube`, `kubectl` e `skaffold` instalados na máquina host com o driver `podman` para deploy e hot-reloading em tempo real.

Instale as seguintes ferramentas na sua máquina host Windows:

- **kubectl**: Ferramenta CLI para executar comandos nos clusters Kubernetes.
- **Skaffold**: Automatiza as pipelines de compilação e deploy com suporte a hot-reloading.
- **OpenLens**: Cliente visual para monitoramento do cluster.
- **Minikube CLI**: Provisiona nós de clusters Kubernetes locais dentro do Podman.
- **Comando de instalação (PowerShell)**:
  ```powershell
  winget install Kubernetes.minikube Kubernetes.kubectl Google.Skaffold Lens.OpenLens
  ```

:::warning[Evite Executar o Skaffold via Containers]
Embora você possa rodar o Skaffold dentro de um container, fazer isso requer a montagem de sockets de containers e o mapeamento de hosts internos. Além disso, a sincronização de arquivos em tempo real (`pnpm k8s:dev`) frequentemente falha ao propagar eventos de sistema de arquivos através dos limites dos containers. Por esse motivo, a instalação do binário nativo do Skaffold localmente é fortemente recomendada.
:::

## 1. Configuração do Podman Compose Container Engine

Para loops de feedback rápidos, rodamos microsserviços e bancos de dados de suporte usando o Podman Compose.

### Configuração da Máquina Podman

1. Inicialize e inicie a máquina Podman padrão:
   ```powershell
   podman machine init
   podman machine start
   ```
2. Verifique o status da máquina Podman:
   ```powershell
   podman info
   ```

### Execução de Scripts do Workspace

Em vez de rodar comandos longos e manuais do Podman Compose, use os filtros e scripts do Turborepo definidos no [package.json](file:///D:/projects/tupynambalucas/package.json) raiz:

- **Iniciar Serviços do Hub**: `pnpm hub:up`
- **Parar Serviços do Hub**: `pnpm hub:down`
- **Resetar Serviços do Hub**: `pnpm hub:reset` (deleta volumes)
- **Iniciar Stack do Cortex**: `pnpm cortex:up`
- **Parar Stack do Cortex**: `pnpm cortex:down`
- **Resetar Stack do Cortex**: `pnpm cortex:reset`
- **Visualizar Logs do Cortex**: `pnpm cortex:logs`

## 2. Configuração do Cluster Local Minikube

Quando for necessário testar políticas de rede, resolução de DNS entre namespaces ou configurações de ingress do Traefik, você deve implantar os workspaces no Minikube.

### Criando o Cluster

Para iniciar o cluster Minikube padrão usando o driver do Podman e configurar a montagem local necessária para os agentes de IA:

```bash
pnpm minikube:up
```

Isso executa:

```bash
minikube start --driver=podman --mount --mount-string ".:/workspace"
```

:::info[Túnel do Minikube]
Como alguns serviços em nosso cluster (como o Traefik) usam IPs do tipo LoadBalancer, você deve abrir um túnel de rede em uma janela separada e persistente de terminal com privilégios de administrador:

```bash
pnpm minikube:tunnel
```

:::

## 3. Visualizando o Cluster

Para monitorar o consumo de recursos, inspecionar logs e gerenciar namespaces de forma visual, usamos o **OpenLens** ou o **Podman Desktop** no host Windows.

1. Defina o contexto ativo para o perfil do Minikube em seu terminal:
   ```bash
   kubectl config use-context minikube
   ```
2. Abra o **OpenLens** ou o **Podman Desktop**.
3. Selecione o contexto do cluster com o nome **minikube**.

## 4. Orquestração Profissional com Skaffold

Usamos o **Skaffold** para automatizar as pipelines de build, deploy e hot-reloading dinâmico.

### Inicializando o Cluster e Workspaces

Fornecemos scripts simplificados no `package.json` raiz para gerenciar o ciclo de vida:

1. **Implantar e Executar em Segundo Plano**:
   Para construir todas as imagens e implantar todos os componentes de plataforma e cortex no Minikube:

   ```bash
   pnpm k8s:up
   ```

2. **Modo de Desenvolvimento Contínuo (Live Hot-Reloading)**:
   Para rodar o Skaffold em modo de desenvolvimento, assistindo alterações no código-fonte e atualizando-as automaticamente dentro dos pods em execução:

   ```bash
   pnpm k8s:dev
   ```

3. **Isolamento de Módulos de Workspace**:
   Você pode implantar workspaces específicos de forma independente para economizar recursos:
   - **Implantar Apenas o Cortex**: `pnpm cortex:dev`
   - **Implantar Apenas a Plataforma**: `pnpm platform:dev`
   - **Implantar Apenas o Studio**: `pnpm studio:dev`

4. **Parar e Limpar**:
   Para remover todos os recursos, namespaces e cargas de trabalho implantados pelo Skaffold:
   ```bash
   pnpm k8s:down
   ```

### Redirecionamento de Portas Locais

O Skaffold configura automaticamente túneis de redirecionamento de portas (port-forward) direcionados a **Serviços** Kubernetes no cluster, em vez de Pods efêmeros. Isso garante mapeamentos locais estáveis de portas que sobrevivem a reinicializações de containers.

| Serviço              | Porta Local | Namespace | Propósito                                 |
| :------------------- | :---------- | :-------- | :---------------------------------------- |
| `agentgateway`       | `8080`      | `cortex`  | Ingress unificado de MCP                  |
| `agentgateway admin` | `15000`     | `cortex`  | Interface Web de gerenciamento do Gateway |
| `memory-api`         | `3006`      | `cortex`  | API REST do serviço de memória            |
| `memory-web`         | `9006`      | `cortex`  | Frontend do serviço de memória            |
| `mcp-inspector`      | `6274`      | `cortex`  | Sandbox do MCP Inspector                  |

## 5. Conectividade do Antigravity CLI

O **Antigravity CLI** se conecta ao proxy de ingress do Cortex (`agentgateway`) utilizando o endpoint do Cloudflare Tunnel definido em `.agents/mcp_config.json`:

```json
"agentgateway": {
  "url": "https://agentgateway-mcp-dev.tupynambalucas.dev",
  "lifecycle": "eager"
}
```

Esta configuração de cliente permite a descoberta e execução transparente de ferramentas MCP em ambientes locais e estações de desenvolvimento remotas em qualquer rede:

- **Modo Cloudflare Tunnel**: O tráfego flui com segurança via `cloudflared` para o serviço `agentgateway` no Minikube, sem necessidade de redirecionamento de portas locais ou alteração de arquivos `/etc/hosts`.
- **Modo de Fallback Local**: Para desenvolvimento offline, o Skaffold faz o port-forward do serviço `agentgateway` para `localhost:8080`.

O `agentgateway` intercepta o payload JSON-RPC de entrada, executa regras CEL de proteção configuradas (via `mcp-guardrails` na porta `9001`) e roteia a chamada para o microsserviço de destino com base nas configurações de targets declaradas em `cortex/gateway/config.yaml`.

## 6. Gerenciamento de Variáveis de Ambiente

Cada contexto de workspace gerencia seus próprios arquivos de ambiente em `<workspace>/infrastructure/.env`.

O Skaffold usa scripts `dotenv-cli` para injetar esses valores como configurações de ambiente de build, que são empacotadas em segredos do Kubernetes via Kustomize:

```yaml
# infrastructure/kubernetes/kustomization.yaml
secretGenerator:
  - name: cortex-secrets
    envs:
      - ../.env
```

:::warning[Colisão de Variáveis de Ambiente de Serviços Kubernetes]
O Kubernetes injeta automaticamente variáveis de ambiente para cada Serviço ativo no mesmo namespace. Se um Serviço for nomeado `mcp-memory`, o Kubernetes configurará a variável de ambiente `MCP_MEMORY_PORT` dentro de cada container para seu URI de conexão (ex: `tcp://10.103.79.15:8080`).

Se sua aplicação tentar ler e converter `process.env.MCP_MEMORY_PORT` em um número de porta, ela retornará `NaN` e falhará. Para evitar essa colisão, sempre adicione um prefixo ou altere o nome das variáveis de ambiente de porta específicas de sua aplicação (ex: use `MEMORY_MCP_PORT` em vez de `MCP_MEMORY_PORT`).
:::
