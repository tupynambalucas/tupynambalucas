# Local Orchestration Setup

This guide details the dual-orchestration environment used in the monorepo. Local development uses two specialized container pipelines:

- **Podman Compose via Podman Desktop**: Used for high-velocity local coding, database testing, and general developer workflows using daemonless containers.
- **Kubernetes via Minikube & Skaffold**: Used to validate configurations, routing, service discovery, and production-like environment policies with automated hot-reloading.

---

## Tooling Prerequisites

To run and manage the local orchestration environment, install the appropriate tools on your machine.

### 1. Podman Container Engine & Podman Desktop

For high-velocity local microservice coding and database testing:

- **Podman Desktop**: GUI and management suite for daemonless Podman machines running over WSL2 on Windows.
- **Podman CLI & Podman Compose**: CLI tools for container and pod management.
- **Install command (PowerShell)**:
  ```powershell
  winget install RedHat.Podman-Desktop RedHat.Podman
  ```

#### Required Podman Desktop Extensions

Inside Podman Desktop (**Settings -> Extensions**), ensure the following extensions are installed and enabled:

1. **Podman Extension**: Core extension for managing Podman machines, images, containers, and volumes.
2. **Compose Extension**: Required to parse and execute `podman compose` workflows for multi-container development.
3. **Kubectl CLI Extension**: Integrates `kubectl` cluster controls and Kubernetes context switching directly inside Podman Desktop.

:::info[No Shell Aliases Policy]
Our project scripts explicitly invoke `podman compose` and `podman exec` directly in [package.json](file:///D:/projects/workspace/package.json). Do not create shell aliases (such as `alias docker=podman`). Using explicit `podman` commands ensures reproducible execution across all developer workstations and CI pipelines.
:::

---

### 2. Kubernetes Environment (Minikube via Podman)

For local Kubernetes testing, routing validation, and deployment pipelines, we use host-installed `minikube`, `kubectl`, and `skaffold` with the `podman` driver for live hot-reloading and cluster deployment.

Install the following tools on your Windows host:

- **kubectl**: CLI tool for executing commands against Kubernetes clusters.
- **Skaffold**: Automates build and deploy pipelines with hot-reloading capabilities.
- **OpenLens**: Visual cluster monitoring client.
- **Minikube CLI**: Provisions local Kubernetes cluster nodes inside Podman.
- **Install command (PowerShell)**:
  ```powershell
  winget install Kubernetes.minikube Kubernetes.kubectl Google.Skaffold Lens.OpenLens
  ```

:::warning[Avoid Running Skaffold via Containers]
Although you can run Skaffold inside a container, doing so requires mounting container sockets and remapping internal hosts. Furthermore, live file synchronization (`pnpm k8s:dev`) often fails to propagate file system events across container boundaries. For this reason, installing the native Skaffold binary locally is strongly recommended.
:::

## 1. Podman Compose Container Engine Setup

For fast feedback loops, we run microservices and backing databases using Podman Compose.

### Podman Machine Configuration

1. Initialize and start the default Podman machine:
   ```powershell
   podman machine init
   podman machine start
   ```
2. Verify Podman engine status:
   ```powershell
   podman info
   ```

### Workspace Script Execution

Instead of running verbose Podman Compose commands manually, use the predefined Turborepo filters and scripts in the root [package.json](file:///D:/projects/workspace/package.json):

- **Start Hub Backing Services**: `pnpm hub:up`
- **Stop Hub Backing Services**: `pnpm hub:down`
- **Reset Hub Backing Services**: `pnpm hub:reset` (deletes volumes)
- **Start Cortex Stack**: `pnpm cortex:up`
- **Stop Cortex Stack**: `pnpm cortex:down`
- **Reset Cortex Stack**: `pnpm cortex:reset`
- **Stream Cortex Logs**: `pnpm cortex:logs`

## 2. Minikube Local Cluster Setup

When you need to test network policies, cross-namespace DNS resolution, or Traefik ingress configurations, you must deploy the workspaces to Minikube.

### Creating the Cluster

To start the default Minikube cluster using the Podman driver and configure the local host mounting required by AI agents:

```bash
pnpm minikube:up
```

This executes:

```bash
minikube start --driver=podman --mount --mount-string ".:/workspace"
```

:::info[Minikube Tunnel]
Since some services in our cluster (like Traefik) use LoadBalancer IPs, you must open a network tunnel in a separate, persistent administrative terminal window:

```bash
pnpm minikube:tunnel
```

:::

## 3. Visualizing the Cluster

To monitor resource consumption, inspect logs, and manage namespaces visually, we use **OpenLens** or **Podman Desktop** on the Windows host.

1. Set the active context to the Minikube profile in your terminal:
   ```bash
   kubectl config use-context minikube
   ```
2. Open **OpenLens** or **Podman Desktop**.
3. Select the cluster context named **minikube**.

## 4. Professional Orchestration with Skaffold

We use **Skaffold** to automate the build, deployment, and live hot-reloading pipelines.

### Launching the Cluster and Workspaces

We provide simplified scripts in the root `package.json` to manage the lifecycle:

1. **Deploy and Run in the Background**:
   To build all images and deploy all platform and cortex components to Minikube:

   ```bash
   pnpm k8s:up
   ```

2. **Continuous Development Mode (Live Hot-Reloading)**:
   To run Skaffold in development mode, watching source code changes and automatically hot-reloading code inside the running pods:

   ```bash
   pnpm k8s:dev
   ```

3. **Workspace Module Isolation**:
   You can deploy specific workspaces independently to save resources:
   - **Deploy Cortex Only**: `pnpm cortex:dev`
   - **Deploy Platform Only**: `pnpm platform:dev`
   - **Deploy Studio Only**: `pnpm studio:dev`

4. **Stop and Clean Up**:
   To tear down all resources, namespaces, and workloads deployed by Skaffold:
   ```bash
   pnpm k8s:down
   ```

### Local Port Forwarding

Skaffold automatically sets up port-forwarding tunnels targeting Kubernetes **Services** inside the cluster rather than ephemeral Pods. This guarantees stable local port mappings that survive container restarts.

| Service              | Local Port | Namespace | Purpose                   |
| :------------------- | :--------- | :-------- | :------------------------ |
| `agentgateway`       | `8080`     | `cortex`  | Unified MCP Ingress       |
| `agentgateway admin` | `15000`    | `cortex`  | Gateway Management Web UI |
| `memory-api`         | `3006`     | `cortex`  | Memory Service REST API   |
| `memory-web`         | `9006`     | `cortex`  | Memory Service Frontend   |
| `mcp-inspector`      | `6274`     | `cortex`  | MCP Inspector Sandbox     |

## 5. Antigravity CLI Connectivity

The **Antigravity CLI** connects to the Cortex ingress proxy (`agentgateway`) using the Cloudflare Tunnel endpoint defined in `.agents/mcp_config.json`:

```json
"agentgateway": {
  "url": "https://agentgateway-mcp-dev.%PROJECT_DOMAIN%",
  "lifecycle": "eager"
}
```

This client configuration enables seamless MCP tool discovery and execution across both local host environments and remote developer workstations on any network:

- **Cloudflare Tunnel Mode**: Traffic routes securely via `cloudflared` to the `agentgateway` Service inside Minikube without requiring local port forwarding or `/etc/hosts` modifications.
- **Local Fallback Mode**: When working offline, Skaffold port-forwards the `agentgateway` Service to `localhost:8080`.

The `agentgateway` intercepts the incoming JSON-RPC payload, runs it through configured CEL guardrails (via `mcp-guardrails` on port `9001`), and routes it to the target microservice based on targets defined in `cortex/gateway/config.yaml`.

## 6. Environment Variable Management

Each workspace context manages its own environment files under `<workspace>/infrastructure/.env`.

Skaffold uses `dotenv-cli` scripts to inject these values as build environment configurations, which are then bundled into Kubernetes secrets via Kustomize:

```yaml
# infrastructure/kubernetes/kustomization.yaml
secretGenerator:
  - name: cortex-secrets
    envs:
      - ../.env
```

:::warning[Kubernetes Service Environment Variable Collision]
Kubernetes automatically injects environment variables for every active Service in the same namespace. If a Service is named `mcp-memory`, Kubernetes sets the environment variable `MCP_MEMORY_PORT` inside every container to its connection URI (e.g. `tcp://10.103.79.15:8080`).

If your application attempts to parse `process.env.MCP_MEMORY_PORT` as a port number, it will yield `NaN` and crash. To prevent this collision, always prefix or rename application-specific port environment variables (e.g., use `MEMORY_MCP_PORT` instead of `MCP_MEMORY_PORT`).
:::
